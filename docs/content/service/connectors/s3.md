## What you need

- A binary built with `--features connector-s3`; S3 is one of five connectors that need a
  specific service installed and running, so it sits outside the default build.
- A reachable S3-compatible endpoint: AWS, MinIO, R2, Ceph RGW or RustFS. One in a container is
  enough:

Runs the same on Linux, macOS and Windows (PowerShell):

<div class="code">
<div class="code-cap"><span>Shell</span><em>a single-disk server on 127.0.0.1:9000</em></div>

```text
docker run --rm -p 9000:9000 -e RUSTFS_ACCESS_KEY=saciaccesskey -e RUSTFS_SECRET_KEY=sacisecretkey -e RUSTFS_ADDRESS=0.0.0.0:9000 rustfs/rustfs:1.0.0-rc.3
```

</div>

- A bucket that already exists. This connector creates none.
- Credentials, unless the bucket is public. `access_key_id` and `secret_access_key` on the node,
  `from_env #true` to read the `AWS_*` environment instead, or `skip_signature #true` for unsigned
  requests.
- The processor component the config names, at `pipelines/orders.wasm`, for the `serve` step.
  [Build your own processor](@/service/processors/build/_index.md) is where that comes from;
  `validate --connectors-only` below runs without it.

## 1. Declare the format

An object carries bytes, so both halves name a declared `transformer` and nothing is inferred from
the key or its suffix.

<div class="code">
<div class="code-cap"><span>KDL</span><em>one declared transformer serves both halves</em></div>

```kdl
transformer "orders_csv" format="csv" {
    options has_headers=#false
}
```

</div>

[csv](@/service/formats/csv.md) and [ndjson](@/service/formats/ndjson.md) read the declared
`schema_fields`. [parquet](@/service/formats/parquet.md), [avro](@/service/formats/avro.md) and
[arrow-ipc](@/service/formats/arrow-ipc.md) read an object's own schema, so a source over one of
those sets `schema_from "object"` to use it rather than projecting onto the declaration.

## 2. Read from a bucket prefix: the source node

<div class="code">
<div class="code-cap"><span>KDL</span><em>the connection node is the same on both halves</em></div>

```kdl
source "orders_in" type="S3Source" component="Order" transformer="orders_csv" {
    config prefix="incoming/orders/" {
        connection {
            bucket "${SACI_S3_BUCKET:-saci-orders}"
            endpoint "${SACI_S3_ENDPOINT:-http://127.0.0.1:9000}"
            access_key_id "${SACI_S3_ACCESS_KEY:-rustfsadmin}"
            secret_access_key "${SACI_S3_SECRET_KEY:-rustfsadmin}"
            allow_http #true
        }
        schema_fields "id" type="Int64" nullable=#false
        schema_fields "amount" type="Float64"
        schema_fields "status" type="Utf8"
    }
}
```

</div>

`prefix` is a byte prefix handed to the service's list API, so end it with a slash to stay inside
one directory. The source lists it once and drains the objects in key order, then reports EOF: there
is no re-list and no tail mode.

`allow_http #true` is what a local server over plain HTTP needs. `endpoint` may be left out for AWS
itself, where `region` picks the endpoint.

`schema_from "object"` hands the format nothing and lets it read the object's own schema, which is
what a self-describing format needs to deliver every column. The schema the object turns out to
carry must still equal `schema_fields` field for field. The default `schema_from "config"` hands
`schema_fields` over instead, so the object is projected onto those columns.

## 3. Write to a bucket prefix: the sink node

<div class="code">
<div class="code-cap"><span>KDL</span><em>flush decides how large one object gets</em></div>

```kdl
sink "orders_out" type="S3Sink" component="Order" transformer="orders_csv" {
    config prefix="processed/orders/" suffix=".csv" {
        flush max_rows=50000 max_bytes=134217728 max_age_ms=60000
        connection {
            bucket "${SACI_S3_BUCKET:-saci-orders}"
            endpoint "${SACI_S3_ENDPOINT:-http://127.0.0.1:9000}"
            access_key_id "${SACI_S3_ACCESS_KEY:-rustfsadmin}"
            secret_access_key "${SACI_S3_SECRET_KEY:-rustfsadmin}"
            allow_http #true
        }
        schema_fields "id" type="Int64" nullable=#false
        schema_fields "amount" type="Float64"
        schema_fields "status" type="Utf8"
    }
}
```

</div>

Every key the sink writes is `{prefix}/{YYYYMMDDTHHMMSS.mmmZ}-{NNNNNN}{suffix}`, so a listing
replays the objects in the order they were written. `suffix` is appended verbatim and nothing is
inferred from the format.

The three `flush` thresholds close the open object on whichever fires first: rows written, encoded
bytes buffered, or milliseconds since the object took its first batch. All three at `0` means
exactly one object, written when the run finishes, which is what a one-shot job usually wants.

## 4. Validate and run

`examples/configs/s3.kdl` drives both halves over one bucket.

Runs the same on Linux, macOS and Windows (PowerShell):

<div class="code-cap"><span>Shell</span><em>no request is sent: validation is offline</em></div>


</div>

`processed/orders`.

## How it delivers

At-least-once. An object leaves the listing only once it has been drained cleanly, so a failure
leaves it at the front and the retry re-reads that same object rather than skipping it. An object
that failed part way through has already handed over some batches, and the retry reopens it at its
start, so those rows arrive twice.

The source lists its prefix once and never re-lists, so later passes of an `interval` or
`continuous` run mode admit no rows.

The open object lives in the sink's memory until a flush threshold fires or the run finishes. A
process killed mid-object loses those rows, because nothing was uploaded.

Whether they come back is the feeding source's business. A Kafka consumer group that has
committed its position past them will not resend, while an S3 source lists its prefix from the
start on the next run and hands every object over again. Size the flush thresholds to how much
loss a restart is allowed to cause.

Neither half opens a connection while the config is built, so `validate` passes against a missing
bucket, a wrong key and an endpoint that is down. All three surface on the first batch.

## Every key

Source, at the top of `config`:

| Key | Type | Default | What it does |
|---|---|---|---|
| `connection` | node | required | bucket, endpoint and credentials |
| `prefix` | string | `""` | the byte prefix listed; end it with a slash to stay in one directory |
| `schema_from` | `"config"` or `"object"` | `"config"` | whether the format is handed `schema_fields` to project onto, or reads the object's own schema and is checked against it |
| `schema_fields` | list of fields | required | the declared column list |

Sink, at the top of `config`:

| Key | Type | Default | What it does |
|---|---|---|---|
| `connection` | node | required | bucket, endpoint and credentials |
| `prefix` | string | `""` | the prefix every generated key sits under |
| `suffix` | string | `""` | appended to the generated key; nothing is inferred |
| `flush` | node | see below | when the open object is uploaded |
| `schema_fields` | list of fields | required | the schema the rows are written with |

A key inside `config` that this connector does not know fails the parse and is named in the error.

### connection

| Key | Type | Default | What it does |
|---|---|---|---|
| `bucket` | string | required | the bucket, which must already exist |
| `endpoint` | string | the AWS endpoint for `region` | the service endpoint |
| `region` | string | `us-east-1` | the region signed for |
| `access_key_id` | string | none | the access key |
| `secret_access_key` | string | none | its secret |
| `session_token` | string | none | a temporary session token |
| `allow_http` | bool | `#false` | allow plain HTTP, which a local server needs |
| `virtual_hosted_style` | bool | `#false` | bucket in the hostname; path style is what a bare host or IP needs |
| `skip_signature` | bool | `#false` | send unsigned requests, for a public bucket |
| `from_env` | bool | `#false` | seed the client from the `AWS_*` environment first, which is how the instance, container and web-identity credential paths are reached |
| `options` | table | empty | every remaining S3 or HTTP client option by its own name; an unrecognised key is an error |

### flush

| Key | Type | Default | What it does |
|---|---|---|---|
| `max_rows` | integer | `100000` | rows before the object is uploaded; `0` disables |
| `max_bytes` | integer | `134217728` | encoded bytes before the object is uploaded; `0` disables |
| `max_age_ms` | integer | `60000` | milliseconds since the object opened; `0` disables |

Rows and bytes are checked after each batch, age on the sink's own ticker, so whichever fires first
closes the object.

## When it refuses to start

| Message | What to change |
|---|---|
| `S3Source config: {e}` / `S3Sink config: {e}` | fix the key the parse error names |
| `S3Source moves bytes and needs a 'transformer' key naming a declared transformer` | add `transformer="<id>"` to the node |
| `S3Source: unknown connection option '{key}': {e}` | remove or correct that `connection.options` entry |
| `S3Sink config requires a 'schema_fields' list` | declare `schema_fields` in the sink's `config` |

Three more wait for the first batch rather than the config check:
`S3Source: listing {prefix}: {e}` means the bucket, the credentials or the endpoint is wrong,
`S3Source: object '{location}' carries schema [...] but the config declared [...]` means a
`schema_from "object"` mismatch, and `S3Sink: put {key}: {e}` means the server refused an upload.
`parquet: declared column 'X' is not in the file (file columns: ...)` means the default
`schema_from "config"` projected onto a column the object does not carry.
